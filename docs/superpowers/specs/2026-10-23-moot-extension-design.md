# Perch · Moot 协作扩展设计

日期：2026-10-23

状态：设计草案，待整体确认；不代表已授权产品实现或发布。

本文整理本次讨论及三版可点击原型中确定的方案。文中的「已确定」来自用户明确选择或确认；「建议」是为便于后续实施提出的默认选择；「待决定」集中列在第 12 节。模型名仅作示例，不构成可用性或能力承诺。

## 1. 目标与使用方式

让用户在 Perch 中统一管理本机 agent 之间的协作：选择可以参与的账号与模型，为不同能力配置执行者与完成方式，并查看委派、审核和圆桌的过程与结果。

用户继续在 Claude、Codex 等熟悉的对话里提出需求。当前对话的 agent 负责判断是否需要协作、组织任务、读取返回结果并交付；Moot 提供可调用的执行程序和技能；Perch 提供扩展生命周期、配置及运行展示。

这里的「本机调用」指通过本机客户端或 CLI 接入模型服务，不代表模型推理在本地离线完成。任务材料会传给实际执行服务，不能把「订阅登录」标为「离线」。

### 已确定的产品原则

- Moot 是可选扩展，用户可在 Perch 中下载、安装、更新和卸载。
- 执行程序保持独立；关闭 Perch 不影响已经启动的任务。
- 安装扩展后提供统一技能家族，逐步统一 `gemini-delegate`、`codex-delegate`、`moot-delegate` 的使用与管理。
- 在用户配置的范围内，主持 agent 可以自动选择并调用其他 agent，无须每次让用户指定。
- 用户明确指定模型时，遵从指定；不可用时说明原因，不擅自替换。
- 订阅调用优先；API 默认关闭，仅在用户事先开启并配置后作为备用。
- 主界面使用「交给谁」「怎么完成」；具体模型、工具和路径放进展开的详细配置。
- 图像生成默认交给 Gemini 订阅接入，要求使用内置生图工具并返回图片文件；API 仅作为开启后的备用。
- 圆桌由当前对话的 agent 主持，可以配置参与模型、各自角色与轮数。
- 第一轮独立发言，后续轮次能看到其他参与者观点并回应分歧。每轮主持人归纳；达到轮数上限后收尾并保留未解决问题。

### 本次不包含

不在设计阶段实施产品、安装真实扩展、触发模型调用或发布版本。不建设通用技能市场、新聊天客户端或云端调度平台，不恢复已删除的文档接力功能。

## 2. 已有基础与真实缺口

截至本次读取本地仓库：

| 项目 | 当前依据与边界 |
| --- | --- |
| Perch | 已管理本机多个客户端账号；macOS 与 Windows 支持范围不完全相同，见 [功能对齐](../../../shared/parity.md) |
| Moot | 现有仓库 README 说明已实现委派、独立审核、Codex／Claude／Antigravity 适配器与运行记录；圆桌和旁观台尚未实现；当前只支持 macOS、订阅登录 |
| 子代理面板 | Perch 历史中曾接入 Moot 记录，之后在 `73d1a1a` 删除；本次是重新设计集成，不能把历史面板算作当前可用功能 |
| 旧 Gemini 委派技能 | 主要用于写稿；启动提示明确要求不用工具，不能直接当作生图调用方案 |
| Gemini 生图 | 需要验证本机 `agy` 无头调用能否使用订阅内置工具并取回图片；本次没有做真实生图验证 |
| API 接入 | Perch 旧的自定义客户端／API 供应商功能已经删除；本扩展需要自己的接入与凭据管理，不能假定旧功能仍可用 |
| 交互原型 | 已验证配置、角色与轮数编辑、逐轮查看和分歧原文跳转；全部使用示例，没有真实任务引擎 |

Moot 原设计中「不放进 Perch」「只支持订阅」的边界，由本次选择的新产品方向取代。旧代码与运行经验是复用基础，不意味着新方案已经实现。

## 3. 架构路线与职责

### 已讨论的两条路线

| 路线 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| Moot 独立安装，Perch 连接管理 | 独立工具用户可直接接入 | 用户需协调安装位置、版本和更新 | 未选择 |
| Perch 管理 Moot 扩展，执行程序独立 | 用户只有一个安装与管理入口；退出界面不影响执行 | Perch 需管理扩展安装状态及版本兼容 | 已选择 |

### 分工

| 部分 | 职责 |
| --- | --- |
| Perch | 下载与管理扩展；编辑用户配置；复用选定账号的引用；展示状态、记录与产物 |
| 技能家族 | 告诉当前 agent 如何判断任务、准备必要背景、发起协作、组织轮次、核实并交付结果 |
| Moot 执行程序 | 解析统一配置；选择接入；启动与跟踪独立进程；执行已授权调用；保存阶段与结果 |
| 接入适配器 | 实现具体 CLI／服务调用、会话续接、能力检查与事件转换 |
| 当前对话的 agent | 担任主持人和最终交付者；不能用另一个模型的自述替代必要核实 |

**建议：** Perch 与执行程序使用同一份用户配置。技能只引用能力与配置，不分别硬编码模型路径。每次运行保存使用时的配置快照；修改预设只影响后续运行。

执行程序的源代码位置、打包方式、进程间接口与本地配置格式交给实施者决定。优先复用已有 Moot，避免在 Swift 与 WPF 中分别重写执行逻辑。本轮仅在 Perch 仓库写设计，不改动外部 Moot 仓库。

## 4. 配置概念

| 概念 | 表达内容 | 示例 |
| --- | --- | --- |
| 账号接入 | 使用哪个账号，以及通过什么程序／服务调用 | Gemini 个人账号，通过 Antigravity CLI |
| 模型设置 | 接入默认模型，或任务明确指定的模型及支持的推理档位 | Codex 的 Astra |
| 工具能力 | 这个具体接入可以调用哪些工具、返回哪些产物 | 内置生图工具，返回图片文件 |
| 能力配置 | 一类任务交给谁、怎么完成、备用方式与额外要求 | 图像生成 → Gemini → 内置生图工具 |
| 协作方式 | 如何组织执行者 | 单次委派、独立审核、圆桌 |
| 席位 | 一场圆桌中的参与模型、角色与职责 | Astra，技术评估，检查实现成本 |
| 运行记录 | 本次实际使用的配置、过程、结果及未完成项 | 第 2 轮 Opus 的发言及主持人小结 |

同一账号接入可服务多个能力；同一模型也可在圆桌中承担不同角色。角色影响任务要求，不赋予额外账号或文件权限。

「已安装程序」「已登录」「模型可选」「所需工具可调用」分别记录。仅有登录状态不能证明生图等工具可用。示例模型名不得成为不可更新的固定支持清单。

## 5. 面板与自动分工

### 5.1 能力配置

每项能力有启用状态、用途说明、交给谁、怎么完成、补充要求及备用顺序。原型示例包含代码审核、文档与文案、前端开发、图像生成、通用委派，并允许添加自定义能力。

主视图展示 agent／账号和完成方式。详细配置展开后提供具体模型覆盖、所需工具、调用路径与账号目录；账号路径等共享信息通过接入配置统一编辑，不复制成多份。

默认路由规则：

1. 本次明确指定的模型／账号优先。指定内容不可满足时返回原因，不悄悄替换。
2. 未指定时，按匹配能力的配置选择执行者与完成方式。
3. 没有专门能力匹配时，使用通用委派配置。
4. 需要备用时，只在用户已经配置并允许的候选中尝试，订阅优先，记录切换原因。
5. API 未开启时，即使订阅不可用也不调用 API；开启不是绕过接入配置、工具能力或凭据检查。
6. 没有可用候选时，明确返回未执行或未完成的原因，由主持人据实处理。

**建议：** 简单任务由当前 agent 自行完成；需要专业工具、独立意见或明确可拆分工作时再委派。不把「自动协作」实现为每项任务都调用其他模型。不以模型品牌或未经验证的评分宣称「最适合」，先使用用户偏好与可用性。

**建议：** API 使用全局默认关闭开关，并要求具体接入及该能力的备用配置允许调用。不能因为某个 CLI 继承了 API 环境变量而绕过开关。切换前保留已有输出；已产生文件改动的任务不能直接当作未执行任务在另一接入重复运行。

### 5.2 接入管理

从 Perch 已管理的账号中选取要开放给扩展的接入，不自动开放所有账号。主视图显示账号、接入类型及可用能力；模型、工具、路径和凭据引用放进详细配置。

订阅接入优先引用现有登录，不复制凭据到技能、项目仓库或运行记录。API 凭据使用系统凭据存储；用户配置保存引用。具体发现与验证方式由各适配器实现，不用某个客户端的登录状态替另一客户端担保。

### 5.3 生图的准确表达

默认配置为：

> 图像生成 → Gemini 订阅账号 → 使用内置生图工具 → 返回图片文件。

Nano Banana 在这条通路中表示生图工具使用的能力，不作为独立订阅账号。工具背后的图像模型与外层对话模型分开记录。API 方式另设为可选备用。

技能自动要求调用工具；不要求用户每次重复输入「使用工具」。返回文字描述或绘图提示词不能标为生图完成。应验证产物存在且能被正常读取，记录工具失败与部分产物。

Gemini CLI 的 Nano Banana 扩展与 Antigravity 的内置工具不是同一接入，计费方式不能按名称推断。官方参考：[Antigravity 模型说明](https://antigravity.google/docs/models)、[Gemini CLI Nano Banana 扩展](https://github.com/gemini-cli-extensions/nanobanana)。真实能力与当前版本仍需本机验证。

## 6. 圆桌配置与轮次协议

### 6.1 已确定的交互

圆桌配置展示参与席位。每个席位选择具体模型、账号、角色，并可编辑角色职责。主持人固定为发起任务的当前对话 agent，不另开一个默认主持模型。

原型提供技术评估、产品设计、用户视角、反方审视和自定义角色。这些角色名称是可调整的预设，不是最终封闭列表。

用户配置轮数上限。一轮定义为：**每位参与者发言一次，再由主持人归纳。** 主持人的小结不额外消耗一个讨论轮次。

### 6.2 每轮可见内容

| 阶段 | 参与者收到什么 | 主持人做什么 |
| --- | --- | --- |
| 第 1 轮 | 相同议题、必要背景、共同限制和自己的角色职责；不提供其他席位的第 1 轮发言 | 收齐结果后归纳共识、分歧和缺失信息 |
| 第 2 轮及以后 | 自己的上下文、上一轮其他参与者观点、主持人小结、未解决分歧和本轮要求 | 要求回应具体观点，归纳变化，更新仍未解决的问题 |
| 达到上限 | 不再发起新的常规讨论轮次 | 汇总共同建议、主持人判断、保留意见和下一步 |

**建议：** 轮内并行，轮间有清晰边界。所有席位看到同一版上一轮材料，不让返回速度影响谁看到了本轮谁的意见。必要压缩时保留观点归属、论据、反对意见及原文索引；不能用主持人一句结论替代其他人的观点。

原型另提供「允许提前结束」开关，默认关闭；这是建议保留的可选项。开启后，主持人可在完整轮次结束时判断是否继续，并记录原因。不能把超时、失败或参与者缺席标成一致通过。

原型的 2–6 个席位、1–10 轮仅为暂定交互边界；正式限制由实施者结合并发、上下文与成本评估确定，不宣称是服务能力限制。

### 6.3 主持与执行的衔接

**建议：** 使用可恢复的阶段记录。执行程序启动当前轮的席位、保存结果，并向发起 agent 返回状态及结果索引；发起 agent 调用读取结果、写入小结和推进下一轮的入口。

Perch 关闭不会中止执行进程，也不会承担模型主持人的工作。若发起 agent 停止工作或对话结束，正在执行的席位仍可完成，会议随后停在「等待主持人」；保留已完成结果，并允许原主持人恢复推进。不能把「退出 Perch 不影响任务」扩大成「原始对话终止后仍会自动完成全部主持工作」。

主持人实际能否在每个目标客户端调用上述入口、等待结果并继续推进，是必须验证的端到端路径。不能假定 Codex 桌面里的所有原生工具在 `codex exec` 中自动存在。

### 6.4 异常和终止

**建议：** 席位失败时保存错误与部分结果，不制造替代发言。同一轮的重试是尝试记录，不增加讨论轮数；已成功席位的结果不重复生成。

圆桌默认不在轮次中悄悄更换模型，以免改变参与者身份。无法恢复时向主持人返回失败，等待其依据用户授权继续、结束或调整；缺席情况下生成的总结必须标明覆盖范围。用户明确指定模型的约束始终保留。

会议达到轮数上限必须停止新增讨论；尚未解决的分歧继续保持开放。手动取消也保留结果，并标记取消及未完成轮次。

## 7. 运行展示与结果语义

### 7.1 列表与详情

列表展示任务标题、发起者、协作方式、实际执行者、开始时间、耗时和状态。支持按状态与文本筛选。详情展示选择依据、订阅／API 方式、备用切换原因、过程事件、最终输出和产物入口。

**建议：** 至少区分未发起、运行中、等待主持人、已结束、失败和已取消；圆桌执行状态与分歧状态分开。模型返回结束、主持人已审阅、用户已验收也不能合并为同一个完成标记。

只展示模型返回的消息、工具事件、命令结果、错误和产物，不承诺提供未公开的内部思考过程。只收集 Moot 自己管理的任务记录，不把用户全部私人聊天正文汇入面板。

### 7.2 圆桌运行详情

- **逐轮发言：** 按轮次切换；查看全部参与者或筛选一个席位；展示模型、角色、状态、发言原文、本轮主持要求与小结。
- **主持人总结：** 分开呈现共同建议、主持人自己的判断、未解决问题和建议下一步；可回看各轮小结。
- **未解决分歧：** 每项记录问题、各方立场、仍缺少的证据或决定、下一步；跳回具体轮次和席位的原文。
- **产物：** 查看或导出总结、发言、图片等实际产生的文件。是否有图片必须以真实文件为准。
- **会议快照：** 固定展示本次参与模型、角色、轮数与结束原因，不随预设更新而变化。

分歧应具有稳定标识，可跟踪首次出现、每轮变化和最终状态。若解决，记录依据；不能仅因主持人省略、轮数耗尽或多数同意就自动标为解决。

### 7.3 最小记录契约（建议）

一次运行至少保存运行 ID、发起端关联、配置快照、实际接入、开始／结束时间、状态、轮次与尝试号。圆桌另保存席位 ID、模型、角色、输入材料引用、发言、主持人小结及分歧引用。产物记录实际文件位置和类型；用量、费用仅在服务可靠返回时显示，未知不填零。

事件及产物引用使用稳定 ID，使界面刷新、进程退出和恢复后仍能定位。同一文件夹不能依靠「最新文件」猜测发言属于哪个席位或轮次。具体存储结构由实施者决定，并提供对已有 Moot 记录的兼容读取或明确迁移方案。

## 8. 技能家族与旧配置迁移

技能按工作方式组织，不按供应商品牌各建一套。暂定入口：`moot-delegate`、`moot-review`、`moot-roundtable`；名称不是已锁定的接口，底层已有 `delegate`／`audit` 能力可复用。

统一接入、配置和记录，同时保留原工作方法的差别：写作只传必要素材；实现按授权读取或修改项目；独立审核避免提前传入主持人的结论。宿主和仓库的权限、提交规范始终适用，不能把旧技能中的固定合并方式直接搬入本仓库。

**建议：** 安装时让用户选择向哪些客户端／账号启用技能。迁移时发现旧技能，展示归属与替代关系；只有明确属于扩展管理的入口才可自动更新或移除。保留旧配置和记录的恢复路径，不默认删除用户自建技能，也不让重复入口长期互相抢触发。

## 9. 安装、更新、退出与卸载

**已确定：** Perch 管理完整生命周期，Moot 执行独立。

**建议的行为：**

- 下载扩展包后记录版本、平台和安装清单；普通用户不需要手工克隆仓库、编辑脚本或处理运行时依赖。
- 安装生成受管理的执行入口和选定客户端的技能入口；个人账号路径与凭据不进入分发包。
- 更新先准备新版本，校验兼容后用于新任务；运行中的任务继续使用它开始时的版本。失败时保留可恢复的旧版本。
- 退出 Perch 只关闭配置与展示界面；后台任务继续写记录，重新打开时可恢复查看。
- 卸载移除扩展拥有的程序与技能入口，默认保留配置、历史和产物；不退出个人客户端、不更改它们的登录。
- 有活动任务时，不直接删除其程序。默认停止接受新任务，待活动任务结束后完成卸载；若用户明确选择取消任务，再保存部分结果并取消。
- 「清除历史和配置」是独立操作，不与普通卸载混在一起。

版本清单、下载校验、原子替换和进程存活检测的具体实现由实施者选择；不为这一个扩展建设通用插件框架。

## 10. 平台、界面与发布范围

当前原型采用独立扩展窗口，包含能力配置、圆桌配置、模型接入和运行记录。用户已确认信息组织方式；原生窗口尺寸、入口位置、侧栏是否合并页面仍是可调整的实现选择。菜单栏面板可保留简短入口与运行状态，不强行容纳长发言。

Perch 同时有 macOS／Windows 产品，但现有 Moot 仅支持 macOS。首版覆盖平台尚待决定，不能将 macOS 原型或测试当作 Windows 已实现。真实实现后再更新 `shared/parity.md` 的用户可见行为与平台状态；设计阶段不修改现状表来宣称功能存在。

扩展来源、公开分发与许可证需按确定的发布范围落实。当前 Moot 旧设计未确定公开许可证；不能将其未授权发布的内容直接当作 Perch 的 MIT 分发资产。本轮只记录设计，不搬入或公开 Moot 源码。

## 11. 后续实施的验证重点

这些是将设计落实为可用产品时的验证场景，不是本次已完成的证据，也不授权现在发起真实调用：

1. 从 Perch 安装扩展，在选定的 Claude／Codex 对话中发现技能；用户只说任务目标，即按能力配置完成真实委派并返回结果。
2. 用户点名模型时准确执行；不可用时不擅自替换。默认模型失败时，仅使用已允许的备用，记录与实际调用一致。
3. API 关闭时任何路由都不调用 API；开启并配置后，订阅优先，备用调用可识别。测试覆盖继承环境变量不会改变计费通路。
4. Gemini 订阅无头调用实际使用生图工具并交付可读图片；不可用时诚实标出失败，API 未开启不自动绕行。
5. 一场真实圆桌验证：首轮独立、后续可见上一轮观点、角色要求有效、每轮有主持归纳、上限停止、未解决问题可追溯。
6. 关闭 Perch 后任务继续；重新打开能查看进展。主持人停止时不会凭空生成总结；恢复后不重复已完成轮次。
7. 任务中断、模型失败、部分产物、更新与卸载均保留必要结果和可理解状态；不破坏真实客户端登录。
8. 旧技能与记录有可恢复的迁移路径；包与仓库不包含真实凭据或私人会话。

验证按风险选择真实端到端路径和关键失败场景，不以测试数量或原型点击替代交付。生图接入、宿主续接等高不确定部分先做小范围可行性验证；不可用时明确降级，不阻塞其他可用能力，也不把目标生图功能宣称已交付。
